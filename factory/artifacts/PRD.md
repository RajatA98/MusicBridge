## Overview

MusicBridge is a cross-platform app — **iOS native and web in v1, Android in v2** — that closes the gap between a piano lesson and the practice that's supposed to follow it. A teacher writes what and how a student should practice. The student opens the app at home and runs a guided session that follows the teacher's intent, with optional MIDI integration that lets the system see what's actually played. The product is the **delivery layer** the BrainLift identifies as missing from the current piano-app market.

The app is built as a single **Expo (React Native) universal codebase** that ships native iOS and a Web build from one source. The teacher portal and student app live in the same codebase, with role-based routing. iOS gets native Core MIDI; web gets Web MIDI API where the browser supports it.

## Goals

- **G1.** A teacher can write a free-text practice assignment and assign it to a paired student in under 60 seconds.
- **G2.** A student can open the app, find their assigned practice, and start a guided session in under 30 seconds.
- **G3.** A guided session walks the student through the teacher's assignment using effective-practice behaviors (segmentation, slow practice, error targeting) — not gamified motivation loops.
- **G4.** When MIDI is connected, the session reacts to what the student plays. When MIDI is not connected, the session still works.
- **G5.** Every assignment has a clear "completed" state the student marks themselves; future versions surface this back to the teacher.
- **G6.** The first ship runs on real users — at least one real teacher and one real student running a real assignment end to end on iOS via TestFlight or on the web build.

**Success metric** — the BrainLift-defined one: *did the student practice productively this week,* not *did the student log in this week.* For v1 this is approximated by completion + teacher feedback at the next lesson.

## Users

| Role | Primary surface | Likely platform | What they do |
|---|---|---|---|
| Teacher | Teacher portal | Web build (laptop/desktop) primarily; iOS app also works | Sign up, invite students, write and assign practice plans, view (later) practice signals |
| Student | Student app | iOS native primarily (where MIDI works); web build for Android / desktop fallback | Accept invite, see assigned practices, run guided sessions with optional MIDI |

**Out of scope as users:** parents, self-taught learners with no teacher, students under 13 without teacher-mediated onboarding (COPPA constraint).

## Core flows

### F1. Teacher onboarding
1. Teacher visits landing page (web) or installs the iOS app, picks **"I'm a teacher."**
2. Signs up with email + password via Firebase Authentication.
3. Lands on teacher dashboard with empty student list.
4. Generates a per-teacher invite link or code.

### F2. Student onboarding (teacher-led)
1. Student receives invite link from teacher (out-of-band: text, email, in-person at lesson).
2. Opens link on iOS (deep-link into the app if installed; else web fallback) or on web.
3. Lands on signup with **"I'm a student"** pre-selected and teacher pairing pre-filled from the invite code.
4. Signs up with email + password.
5. Lands on student dashboard, automatically paired with the inviting teacher.

### F3. Teacher creates and assigns practice
1. Teacher opens dashboard, sees student list.
2. Picks a student → "Assign practice."
3. Writes free-text assignment (single text area). Examples shown as placeholder hints: *"Practice C major scale, hands separate, 60 bpm, focus on smooth thumb-under in measure 2."*
4. Optional fields: due date, estimated duration.
5. Saves → assignment appears in student's queue.

### F4. Student starts a session
1. Student opens dashboard. Sees list of assigned practices, most recent first.
2. Each item shows: assignment text preview, teacher name, date assigned, status (new / in progress / completed).
3. Taps an assignment → "Practice with AI tutor."

### F5. Guided session (with or without MIDI)
1. Session view loads. Reads the teacher's assignment text.
2. **MIDI prompt:** "Connect a MIDI keyboard? (Optional)" — student can dismiss.
3. **If MIDI connected (iOS native or Web MIDI–capable browser):** establishes a MIDI connection, displays "Listening to: [device name]."
4. **AI tutor (v1, thin-slice):** displays the teacher's assignment, then walks the student through it as a numbered checklist of guided steps generated by Claude from the teacher's text. Each step is a single instruction (e.g., "Play C major scale ascending, hands separately, slowly. Stop on any error and retry that note.").
5. As the student progresses, they mark each step done. If MIDI is connected, the session can show what was played but does not block progression on MIDI signal.
6. At end, student marks session complete → returns to dashboard.

### F6. Teacher views student progress
1. Teacher dashboard shows each paired student with their last assignment status.
2. Tap into a student → list of past assignments with completion status.
3. **v1 scope:** completion status only. No practice-quality signals. Practice quality dashboard is v2.

## Functional requirements

### Authentication & accounts
- **FR-A1.** Email + password signup via **Firebase Authentication** (JS SDK v12+). On native, persistence via `getReactNativePersistence(AsyncStorage)`. On web, default origin-scoped local persistence.
- **FR-A2.** Each user has a single role (teacher OR student), set at signup, immutable in v1. Role stored in Firestore `users` doc.
- **FR-A3.** Student records a `teacherId` reference established at signup via invite link/code. One student → one teacher in v1.
- **FR-A4.** Teacher can generate and view their unique invite link/code. Regenerating invalidates the old one.
- **FR-A5.** Logout works on both iOS and web.
- **FR-A6.** Authenticated session persists across app reloads / page refreshes (Firebase SDK persistence).
- **FR-A7.** At invite creation, teacher must select an **age attestation** for the invited student: `self-attested-13+` or `school-authorized`. The selection is recorded in the immutable `invite_audits` collection with `teacherId`, `studentEmail`, `attestedOver13`, `attestedAt`, and `termsVersion`.

### Teacher portal
- **FR-T1.** Dashboard lists all paired students.
- **FR-T2.** "Assign practice" form: required text area for the assignment, optional due date and duration.
- **FR-T3.** Assignments list per student, sorted by date (newest first), showing status.
- **FR-T4.** Teacher can edit or delete an assignment until the student has started it.
- **FR-T5.** Teacher cannot view assignments belonging to other teachers' students. Enforced by Firestore Security Rules.

### Student app
- **FR-S1.** Dashboard lists assigned practices, sorted by date (newest first).
- **FR-S2.** Each practice shows: teacher name, assignment text preview, assigned date, status.
- **FR-S3.** Status values: `new`, `in_progress`, `completed`.
- **FR-S4.** Starting a session moves status to `in_progress`. Completing moves it to `completed`.
- **FR-S5.** Student can re-open a completed assignment and start a fresh session.

### Guided session
- **FR-G1.** Session view fetches the teacher's assignment text and presents it.
- **FR-G2.** AI tutor generates a checklist of 3–7 guided steps from the teacher's text using Claude API. Generation runs in a Firebase Cloud Function (server-side, holds the API key).
- **FR-G3.** Each step is plain text, displayed one at a time with progress dots at top.
- **FR-G4.** Student can mark each step done; advance to next step.
- **FR-G5.** AI generation runs once at session start; the generated step text is persisted with the session document so revisits are stable.
- **FR-G6.** Session view degrades gracefully if AI generation fails: falls back to displaying the raw teacher text and a single "mark complete" button.
- **FR-G7.** Step text is **synthesized to speech at runtime** on first display via `expo-speech` (native) or Web `SpeechSynthesis` (web). Audio is **not** pre-generated or stored as a file in v1. Replay button (↻) re-synthesizes on demand. Server-side audio generation and storage is a v1.5 path tied to the ElevenLabs upgrade.

### MIDI (optional)
- **FR-M1.** "Connect MIDI keyboard" button in session view.
- **FR-M2.** **iOS native:** Core MIDI via React Native MIDI library (specific library locked in Decide). Connects to USB or Bluetooth MIDI devices.
- **FR-M3.** **Web build:** Web MIDI API where supported (Chrome desktop, Edge desktop, Android Chrome).
- **FR-M4.** When connected, display the connected device name and the last 4 notes played. Default rendering is neutral (no color logic). Tonality-based green/gray coloring is a v1.5 feature gated on a structured tonality field on the assignment, which v1 does not collect.
- **FR-M5.** No required MIDI interaction — MIDI is informational in v1, not validating session completion.
- **FR-M6.** Graceful unavailability: on platforms without MIDI support (iOS Safari web build, Firefox web build), show a clear notice — "MIDI is not available on this browser. Use the iOS app or Chrome / Edge desktop." Session continues normally without MIDI.

### Data model (v1, Firestore collections — root collections only)
- **users** — `{ uid, email, role (teacher | student), teacherId (string, students only), createdAt }` — keyed by Firebase Auth `uid`.
- **invites** — `{ teacherId, code (unique), active, createdAt }` — keyed by code.
- **invite_audits** — `{ teacherId, studentEmail, attestedOver13, attestedAt, termsVersion }` — immutable, write-once at invite creation. Required for COPPA audit trail.
- **assignments** — `{ teacherId, studentId, body (text), dueDate, estimatedDuration, status, createdAt, updatedAt }`.
- **sessions** — `{ assignmentId, teacherId, studentId, steps (array of generated checklist text), startedAt, completedAt }`. Audio refs added in v1.5 when a server-side TTS provider is introduced.

**Required composite indexes:**
- `assignments(studentId ASC, createdAt DESC)`
- `assignments(teacherId ASC, studentId ASC, createdAt DESC)`
- `sessions(assignmentId ASC, startedAt DESC)`

## Non-functional requirements

### Performance
- **NFR-P1.** Initial dashboard load: under 2 seconds on a fresh session over a typical broadband or LTE connection.
- **NFR-P2.** AI step-generation: under 5 seconds end-to-end. Loading state visible.
- **NFR-P3.** MIDI connection: established within 1 second of user tapping connect.

### Platform support
- **NFR-B1.** **iOS native:** iOS 16+ via TestFlight build (App Store submission deferred). MIDI fully supported via Core MIDI.
- **NFR-B2.** **Web (Expo web export, hosted on Firebase Hosting):**
  - Chrome desktop (latest two versions): full support including MIDI.
  - Edge desktop (latest two versions): full support including MIDI.
  - Safari desktop and iOS Safari: full support except MIDI (graceful fallback per FR-M6).
  - Android Chrome: full support including MIDI.
  - Firefox: full support except MIDI.
- **NFR-B3.** **Android native:** out of scope for v1, deferred to v2.
- **NFR-B4.** Responsive layout on web for desktop and mobile widths.
- **NFR-B5.** Touch-friendly tap targets (44pt minimum) across all surfaces.

### Privacy & data
- **NFR-D1.** No collection of personal data beyond email and role at signup. No name fields, no birth dates, no addresses in v1.
- **NFR-D2.** All assignment text and session data scoped to the owning teacher-student pair. Enforced by **Firestore Security Rules** that check `teacherId == request.auth.uid` (teacher reads) or `studentId == request.auth.uid` (student reads). Rules **do not cascade** into subcollections — every nested `match` block must repeat its own auth checks.
- **NFR-D3.** Students under 13 are out of scope for v1. At invite, teacher must select age attestation (`self-attested-13+` or `school-authorized`). Attestation is recorded immutably in the `invite_audits` collection (FR-A7).
- **NFR-D4.** No third-party user-analytics SDKs in v1 (no Mixpanel, PostHog, Amplitude). **Firebase Analytics is explicitly DISABLED across the entire app in v1** — both teacher and student surfaces. One Expo codebase makes a per-role split easy to misconfigure. Configure opt-out via `firebase.json` and platform-specific flags. Sentry (error monitoring, not user analytics) is the only client-side observability tool. Cloud Functions structured logs handle server-side.
- **NFR-D5.** Cloud Functions enforce **App Check** (`enforceAppCheck: true`) on all callable endpoints to prevent abuse from non-app clients.
- **NFR-D6.** Anthropic API key stored via `defineSecret('ANTHROPIC_API_KEY')` in Cloud Functions secrets, never in client.

### Reliability
- **NFR-R1.** Auth, Firestore, and Cloud Function failures must not lose user data. Assignments are persisted to Firestore before AI generation runs; AI failures fall back gracefully (FR-G6).
- **NFR-R2.** No data loss on app reload during a session — session state is persisted to Firestore as steps are completed.
- **NFR-R3.** AI generation Cloud Function: 30s timeout, `minInstances: 1` to mitigate cold starts, retry policy = single bounded retry on 429/500/529 with `retry-after` honored, fallback returns raw teacher text.

### Observability
- **NFR-O1.** Sentry instrumentation in the Expo client (native + web) captures crashes and unhandled errors.
- **NFR-O2.** Cloud Functions emit structured logs via `firebase-functions/logger`. Anthropic API errors, fallback events, and auth-failure events are logged at structured-event level.
- **NFR-O3.** No Firebase Crashlytics in v1 (would force native Firebase modules and adds no web coverage).

### Accessibility (v1 floor)
- **NFR-X1.** Keyboard-navigable on web; native iOS keyboard navigation works in app.
- **NFR-X2.** Sufficient color contrast (WCAG AA on text).
- **NFR-X3.** Form fields have labels (web) and accessibility labels (iOS).
- Deeper a11y (full VoiceOver / screen-reader optimization, dynamic-type support, ARIA live regions) deferred to v2.

## Non-goals (v1)

- Teacher-uploaded demonstration videos
- Hand-movement animations
- Audio-only detection (acoustic piano support)
- **Android native** (deferred to v2 — Expo codebase will be ready, just not built or distributed in v1)
- Teacher analytics / practice-quality dashboard
- Payments and subscriptions
- Pre-built lesson library and lesson authoring UI
- Structured assignment forms (v1 is plain text)
- Real-time tone, posture, technique evaluation
- Parent-facing surfaces
- Multi-teacher students (one student → one teacher in v1)
- Student-to-student social features
- Conversational AI tutor (v2 — v1 ships the thin-slice checklist tutor)
- App Store submission (TestFlight only in v1)

## Inheritance from PROBLEM_SUMMARY and BrainLift

All BrainLift-derived constraints from `PROBLEM_SUMMARY.md` carry forward unchanged:

- No gamification of the experience (no points, no streaks, no badges as primary motivation mechanic).
- Teacher-extending, not teacher-replacing.
- Success = student practiced productively, not student opened the app.
- 21% deliberate-practice ceiling acknowledged — product does not promise mastery, it promises better practice transfer.
- The v1 must validate the **delivery mechanism** before investing in richer AI pedagogy.
