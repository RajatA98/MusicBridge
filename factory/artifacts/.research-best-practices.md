## 1. Expo + Firebase wiring (JS SDK vs `@react-native-firebase`)

**Recommendation:** For MusicBridge v1 (universal app: iOS + web, Android v2), use the **Firebase JS SDK v12+** in an Expo Dev Build. JS SDK covers the only services you need (Auth, Firestore, Functions callable, Hosting). Switch to `@react-native-firebase` only if/when you add Crashlytics, Analytics, or Performance Monitoring native modules. Mixing both in the same app is a known "dual package hazard" — pick one.

**Auth init pattern (Expo, persistence on iOS, memory on web):**
```ts
// firebase.ts
import { initializeApp, getApps } from 'firebase/app';
import {
  initializeAuth,
  getAuth,
  // @ts-ignore — present in RN bundle, missing from TS types as of firebase 12.x
  getReactNativePersistence,
  browserLocalPersistence,
} from 'firebase/auth';
import AsyncStorage from '@react-native-async-storage/async-storage';
import { Platform } from 'react-native';
import { getFirestore } from 'firebase/firestore';
import { getFunctions } from 'firebase/functions';

const app = getApps().length ? getApps()[0] : initializeApp(firebaseConfig);

export const auth =
  Platform.OS === 'web'
    ? getAuth(app) // defaults to browserLocalPersistence in modern browsers
    : initializeAuth(app, {
        persistence: getReactNativePersistence(AsyncStorage),
      });

export const db = getFirestore(app);
export const functions = getFunctions(app, 'us-central1');
```

**Cloud Function Admin SDK pattern (Gen 2, callable):**
```ts
// functions/src/index.ts
import { onCall, HttpsError } from 'firebase-functions/v2/https';
import { initializeApp } from 'firebase-admin/app';
import { getFirestore } from 'firebase-admin/firestore';
initializeApp();
const db = getFirestore();

export const createAssignment = onCall(
  { region: 'us-central1', cors: true, timeoutSeconds: 60, memory: '512MiB', minInstances: 0 },
  async (req) => {
    if (!req.auth) throw new HttpsError('unauthenticated', 'Sign in required');
    const role = req.auth.token.role;
    if (role !== 'teacher') throw new HttpsError('permission-denied', 'Teachers only');
    // ...write doc
  }
);
```

**Top gotchas:**
1. `firebase@^12` is required for Expo SDK 53+. Older versions hit ESM "dual package" errors.
2. `getReactNativePersistence` exists at runtime but TS types miss it on some builds — `@ts-ignore` is the documented workaround. Without it, auth state silently drops to memory persistence and users get logged out on app restart.

**Sources:**
- [Expo: Using Firebase](https://docs.expo.dev/guides/using-firebase/)

## 2. Firestore data model + Security Rules

**Recommendation:** Use **root collections with explicit ownership fields** (`teacherId`, `studentId`) rather than deep subcollections. Subcollections are fine for tightly-scoped, never-cross-queried data (e.g., `assignments/{id}/sessions/{sid}`), but root-level keeps composite queries (e.g., "all assignments for student X across teachers") cheap. Multi-tenancy guides recommend a `tenantId`/`teacherId` field for max flexibility.

**Proposed shape:**
```
/users/{uid}                 { role: 'teacher'|'student', email, displayName, createdAt }
/invites/{inviteId}          { teacherId, code, email?, status, expiresAt }
/assignments/{assignmentId}  { teacherId, studentId, status, steps[], createdAt, dueAt }
/assignments/{aid}/sessions/{sid}  { studentId, startedAt, completedAt, events[] }
/auditLogs/{logId}           { actorUid, action, targetPath, ts, meta }
```

**Security Rules (with custom claim `role`):**
```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    function isSignedIn()      { return request.auth != null; }
    function isTeacher()       { return isSignedIn() && request.auth.token.role == 'teacher'; }
    function isStudent()       { return isSignedIn() && request.auth.token.role == 'student'; }
    function uid()             { return request.auth.uid; }

    // users: each user reads/writes only own doc; teachers can read student docs they own
    match /users/{userId} {
      allow read: if uid() == userId
        || (isTeacher() && resource.data.teacherId == uid());
      allow create: if uid() == userId;
      allow update: if uid() == userId
        && !(request.resource.data.diff(resource.data).affectedKeys()
              .hasAny(['role','teacherId']));    // role/teacher link is server-only
    }

    // assignments: teacher owns; student can read own
    match /assignments/{assignmentId} {
      allow read: if (isTeacher() && resource.data.teacherId == uid())
                  || (isStudent() && resource.data.studentId == uid());
      allow create: if isTeacher() && request.resource.data.teacherId == uid();
      allow update, delete: if isTeacher() && resource.data.teacherId == uid();

      match /sessions/{sessionId} {
        allow read: if (isTeacher() &&
                        get(/databases/$(database)/documents/assignments/$(assignmentId)).data.teacherId == uid())
                    || (isStudent() && resource.data.studentId == uid());
        allow create: if isStudent() && request.resource.data.studentId == uid();
        allow update: if isStudent() && resource.data.studentId == uid();
      }
    }

    match /invites/{inviteId} {
      allow read: if isTeacher() && resource.data.teacherId == uid();
      allow create: if isTeacher() && request.resource.data.teacherId == uid();
      allow update, delete: if isTeacher() && resource.data.teacherId == uid();
    }

    // audit logs: server-only via Admin SDK; clients never read
    match /auditLogs/{id} {
      allow read, write: if false;
    }
  }
}
```

**Required composite indexes (add to `firestore.indexes.json`):**
- `assignments` — `teacherId ASC, createdAt DESC` (teacher dashboard list)
- `assignments` — `studentId ASC, status ASC, dueAt ASC` (student "what's due")
- `invites` — `teacherId ASC, status ASC, expiresAt ASC`

**Top gotchas:**
1. Rules at a parent path do **not** cascade to subcollections — every match block needs its own rules. Easy to ship a wide-open subcollection by mistake.
2. `get()` lookups in rules cost a document read each and count toward billing/rate limits. Prefer custom claims for the hot path; reserve `get()` for rare ownership checks.

**Sources:**
- [Firebase: Structuring Security Rules](https://firebase.google.com/docs/firestore/security/rules-structure)
- [Firebase: Custom claims & Security Rules](https://firebase.google.com/docs/auth/admin/custom-claims)
- [Firebase: Role-based access solutions](https://firebase.google.com/docs/firestore/solutions/role-based-access)
- [Wild.codes: Firestore multi-tenancy](https://wild.codes/candidate-toolkit-question/how-do-you-model-firestore-multi-tenant-data-for-speed-and-safety)

## 3. Cloud Function calling Claude (Haiku 4.5)

**Recommendation:** Use a **Gen 2 Callable Function** (`onCall` from `firebase-functions/v2/https`). For 3–7 step JSON generation, **prefer single-shot (non-streaming)** — it's simpler, the response is small (~1–3 KB), and Haiku 4.5 is fast enough that the user's "loading" state is acceptable. Only adopt streaming via `response.sendChunk` if generation routinely exceeds ~3s of perceived latency.

**Pattern:**
```ts
import { onCall, HttpsError } from 'firebase-functions/v2/https';
import { defineSecret } from 'firebase-functions/params';
import Anthropic from '@anthropic-ai/sdk';

const ANTHROPIC_KEY = defineSecret('ANTHROPIC_API_KEY');

export const generatePracticePlan = onCall(
  {
    region: 'us-central1',
    secrets: [ANTHROPIC_KEY],
    timeoutSeconds: 60,
    memory: '512MiB',
    minInstances: 1,           // keep 1 warm — ~$5–10/mo, eliminates cold-start UX hit
    concurrency: 80,           // Gen 2 default; safe for stateless Claude calls
  },
  async (req) => {
    if (!req.auth) throw new HttpsError('unauthenticated', 'sign in');
    if (req.auth.token.role !== 'teacher') throw new HttpsError('permission-denied', 'teachers only');

    const client = new Anthropic({ apiKey: ANTHROPIC_KEY.value() });
    try {
      const msg = await client.messages.create({
        model: 'claude-haiku-4-5',
        max_tokens: 1024,
        system: 'You are a piano practice coach. Output strict JSON matching schema X.',
        messages: [{ role: 'user', content: req.data.prompt }],
      });
      const text = msg.content[0].type === 'text' ? msg.content[0].text : '';
      return { plan: JSON.parse(text) };
    } catch (e: any) {
      // Graceful fallback: return a canned 3-step plan rather than 500
      console.error('claude_error', { uid: req.auth.uid, err: e?.message });
      return { plan: FALLBACK_PLAN, degraded: true };
    }
  }
);
```

**Cold-start mitigation:** `minInstances: 1` is the simplest. Gen 2 also supports concurrency >1 per instance, so one warm instance can serve a 50-tester pilot easily.

**Top gotchas:**
1. Don't put the API key in `functions.config()` (deprecated in Gen 2). Use `defineSecret` + Secret Manager — the secret is mounted only at runtime and is never in source.
2. Anthropic may return `content[0]` with `type: 'tool_use'` if you enable tools; always type-check before parsing as text.

**Sources:**
- [Firebase: Streaming callable functions + Genkit](https://firebase.blog/posts/2025/03/streaming-cloud-functions-genkit/)
- [Firebase: Call functions from your app (callable)](https://firebase.google.com/docs/functions/callable)
- [Firebase: Tips & tricks (cold start, concurrency)](https://firebase.google.com/docs/functions/tips)

## 4. iOS Universal Links via Expo Router (FDL is dead)

**Recommendation:** Host the AASA file on **Firebase Hosting at `/.well-known/apple-app-site-association`** (no extension) with `Content-Type: application/json`, and set `appAssociation: "NONE"` in `firebase.json` to stop Firebase from overriding the file with its (now-deprecated) Dynamic Links default. Configure `ios.associatedDomains` in `app.config.ts`.

**`app.config.ts`:**
```ts
export default {
  expo: {
    scheme: 'musicbridge',
    ios: {
      bundleIdentifier: 'com.musicbridge.app',
      associatedDomains: ['applinks:musicbridge.app', 'applinks:www.musicbridge.app'],
    },
    android: {
      package: 'com.musicbridge.app',
      intentFilters: [{
        action: 'VIEW',
        autoVerify: true,
        data: [{ scheme: 'https', host: 'musicbridge.app' }],
        category: ['BROWSABLE', 'DEFAULT'],
      }],
    },
  },
};
```

**`firebase.json`:**
```json
{
  "hosting": {
    "public": "web-build",
    "appAssociation": "NONE",
    "headers": [
      {
        "source": "/.well-known/apple-app-site-association",
        "headers": [{ "key": "Content-Type", "value": "application/json" }]
      },
      {
        "source": "/.well-known/assetlinks.json",
        "headers": [{ "key": "Content-Type", "value": "application/json" }]
      }
    ]
  }
}
```

**`public/.well-known/apple-app-site-association`:**
```json
{
  "applinks": {
    "details": [{
      "appIDs": ["TEAMID.com.musicbridge.app"],
      "components": [
        { "/": "/invite/*", "comment": "teacher invite links" },
        { "/": "/assign/*", "comment": "assignment links" }
      ]
    }]
  }
}
```

**Deferred deep linking (FDL replacement, 2026):** There is no first-party drop-in. The recommended pattern is:
1. Send the user to `https://musicbridge.app/invite/<code>`. If app is installed → Universal Link opens it.
2. If not installed, the web page captures the code, redirects to the App Store with a custom referral param, and stores the code in `localStorage`/cookies.
3. After install + first launch, the app opens, hits a `/me/pending-invite` Cloud Function or reads a `Clipboard`/`UIPasteboard` token (with user consent), and resolves the invite.

This is verified in the Firebase migration guide ("Migrate from Dynamic Links to App Links & Universal Links"); the deferred-install handoff itself is application-specific — Firebase no longer provides it.

**Top gotchas:**
1. The AASA file must have **no `.json` extension** and must be served as `application/json`. Firebase Hosting's default behavior used to serve its own AASA — `appAssociation: "NONE"` is mandatory to disable that.
2. iOS aggressively caches AASA. Updating components requires either `swcutil` testing or deleting/reinstalling the app on the device. Use Apple's CDN check: `https://app-site-association.cdn-apple.com/a/v1/musicbridge.app`.

**Sources:**
- [Expo: iOS Universal Links](https://docs.expo.dev/linking/ios-universal-links/)
- [Expo blog: Universal Links and App Links with Expo Router and EAS Hosting](https://expo.dev/blog/universal-and-app-links)
- [Firebase: Migrate from Dynamic Links to App Links & Universal Links](https://firebase.google.com/support/guides/app-links-universal-links)
- [Firebase Hosting AASA gist (mbleigh)](https://gist.github.com/mbleigh/c9140c97a342b9d2e7cd727e21b6268f)

## 5. NativeWind v4 in current Expo SDK

**Recommendation:** Pin to a known-good NativeWind v4 release (current discussion thread tracks "officially recommended versions"); avoid 4.2.0 which broke Expo 53. Treat NativeWind on web as a CSS-Modules build via Metro — make sure your `metro.config.js` uses `withNativeWind`, and keep a `global.css` at the project root with the Tailwind directives.

**Setup:**
```js
// metro.config.js
const { getDefaultConfig } = require('expo/metro-config');
const { withNativeWind } = require('nativewind/metro');
const config = getDefaultConfig(__dirname, { isCSSEnabled: true });
module.exports = withNativeWind(config, { input: './global.css' });
```
```css
/* global.css */
@tailwind base;
@tailwind components;
@tailwind utilities;
```
Import once at the root: `import './global.css'` in `app/_layout.tsx`.

**Top gotchas:**
1. Hot-reload sometimes won't apply newly added classes — clear Metro cache (`npx expo start -c`) after adding new utility variants.
2. On Windows specifically there's an unresolved `global.css.web.css` Metro error (#1492). Mac/Linux dev environments are unaffected, but CI on Windows runners will fail.

## 6. `@motiz88/react-native-midi` production readiness

**Recommendation:** **Vendor and patch.** The repo is explicitly marked `[WIP]` by the author (Moti Zilberman, Expo team). It builds via Expo Modules and is technically usable, but it has not seen a release cadence sufficient to depend on for a production iOS app shipping to TestFlight in 2026. For v1, fork into a `packages/react-native-midi` workspace (or use `patch-package`), pin its peer deps, and budget time to reproduce the iOS build in EAS. For v2 (Android), plan to write a small custom Expo Module for `MIDIClient` parity rather than wait on upstream.

**Verified:** GitHub repo title is literally `[WIP] Web MIDI implementation for React Native using Expo Modules`. The Expo blog post "Building a MIDI-over-Bluetooth app using Expo Modules" (the canonical reference) treats this library as a starting point, not a turnkey dependency. Last release cadence and recent commit activity on the GitHub page could not be fully verified in this session (WebFetch was disabled) — confirm via `gh repo view motiz88/react-native-midi` before committing.

**Top gotchas:**
1. iOS requires `audio` background mode and the `NSBluetoothAlwaysUsageDescription` Info.plist string for BLE MIDI. Forgetting these is the most common TestFlight rejection vector for MIDI apps.
2. The Web MIDI API surface differs subtly between Chrome (full) and Safari (still partial as of 2026). Plan to fall back to keyboard input on Safari web.

## 7. iOS Speech Synthesis + Web SpeechSynthesis

**Recommendation:** Use **`expo-speech`** on iOS (and Android v2). Both `expo-speech` and `react-native-tts` wrap the same `AVSpeechSynthesizer`, but `expo-speech` is officially supported in managed/dev-build flow with no extra config. On web, use the `window.speechSynthesis` API directly behind a small wrapper that handles Chrome's async `voiceschanged` event.

**Cross-platform wrapper sketch:**
```ts
// tts.ts
import * as Speech from 'expo-speech';
import { Platform } from 'react-native';

export async function speak(text: string, opts: { lang?: string; rate?: number } = {}) {
  if (Platform.OS === 'web') {
    const voices = await getWebVoices();
    const u = new SpeechSynthesisUtterance(text);
    u.lang = opts.lang ?? 'en-US';
    u.rate = opts.rate ?? 1;
    u.voice = voices.find((v) => v.lang.startsWith(u.lang)) ?? null;
    window.speechSynthesis.cancel();      // interrupt anything in flight
    window.speechSynthesis.speak(u);
    return;
  }
  Speech.stop();                          // interrupt
  Speech.speak(text, { language: opts.lang, rate: opts.rate });
}

function getWebVoices(): Promise<SpeechSynthesisVoice[]> {
  return new Promise((resolve) => {
    const v = window.speechSynthesis.getVoices();
    if (v.length) return resolve(v);
    window.speechSynthesis.onvoiceschanged = () =>
      resolve(window.speechSynthesis.getVoices());
  });
}
```

**Top gotchas:**
1. Chrome returns `[]` from `getVoices()` on first call — must wait for `onvoiceschanged`. Safari/Firefox return synchronously. Without the wrapper, voice selection silently fails on Chrome.
2. iOS interrupts: call `Speech.stop()` before `speak()` if you want barge-in; otherwise the new utterance queues. AVSpeechSynthesizer also pauses if a phone call comes in — observe `Speech.isSpeakingAsync()` to keep UI in sync.

**Sources:**
- [Expo: Speech](https://docs.expo.dev/versions/latest/sdk/speech/)
- [MDN: SpeechSynthesis](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesis)
- [easy-speech (cross-browser wrapper)](https://github.com/leaonline/easy-speech)

## 8. K-12 ed-tech privacy (COPPA-aware teacher attestation)

**Recommendation:** For v1 free pilot, treat the teacher as the **gatekeeper** and require an explicit attestation at student-invite creation: "I confirm this student is age 13 or older, **OR** my school has obtained parental consent under the COPPA school-authorization exception for this user." Store the attestation as an immutable record. Even though the FTC declined to codify the school-authorization exception in the **April 22, 2026** updated COPPA Rule, FTC enforcement guidance still permits it for educational use limited to the contracted service. So explicitly logging the basis is what protects you.

**Data shape:**
```
/invites/{id} {
  teacherId, code, email?, status,
  attestation: {
    version: 'v1-2026-04',
    teacherUid, signedAt: <ts>,
    studentIs13OrOlder: bool,
    schoolConsentBasis: 'self-attested-13+' | 'school-authorized' | null,
    schoolName?: string,
  },
  expiresAt
}

/auditLogs/{id} {
  actorUid, action: 'invite.create'|'student.signup'|'assignment.delete'|'data.export'|'data.delete',
  targetPath, ts, ip?, userAgent?, meta
}
```

**Data minimization (required by 2026 rule):** collect only what the educational service needs. For MusicBridge that means: name (display only), email (auth + invite), MIDI session events. Do **not** collect device identifiers, geolocation, or any behavioral analytics signals tied to student accounts.

**Firebase-specific gotchas:**
1. Firebase Auth stores email + UID in a US-region GCP project by default. For schools that ask, you may need to confirm this and offer a regional Firestore (multi-region `nam5` is fine; document it).
2. Firebase Analytics auto-collects ad identifiers — **do not** enable Analytics on the student-side build, or initialize it with `analytics_collection_enabled = false`. This is the single biggest COPPA trip-wire in Firebase apps.

**Sources:**
- [DEV: What is COPPA in 2026](https://dev.to/bhavesh_pawar_8205920953a/what-is-coppa-in-2026-and-when-does-it-apply-to-your-edtech-product-56dd)
- [Public Interest Privacy Center: New COPPA Update](https://publicinterestprivacy.org/new-coppa-update/)
- [FTC: COPPA Guidance for Ed Tech](https://www.ftc.gov/business-guidance/blog/2020/04/coppa-guidance-ed-tech-companies-schools-during-coronavirus)

## 9. TestFlight via EAS Build (2026 happy path)

**Recommendation:** Use `eas build -p ios --profile production` then `eas submit -p ios` (or the unified `npx testflight` command). For a 50-tester pilot, **internal testing only** is the simplest — up to 100 users, no Beta App Review, available immediately on processing. Move to External (up to 10,000, requires Apple's Beta App Review, ~24h) only once you exceed 100.

**`eas.json`:**
```json
{
  "cli": { "version": ">= 12.0.0" },
  "build": {
    "production": {
      "ios": { "autoIncrement": "buildNumber" },
      "channel": "production"
    },
    "preview": {
      "distribution": "internal",
      "ios": { "simulator": false }
    }
  },
  "submit": {
    "production": {
      "ios": {
        "appleId": "you@example.com",
        "ascAppId": "1234567890",
        "appleTeamId": "ABCDE12345"
      }
    }
  }
}
```

**Happy path:**
1. `eas credentials` once to generate/upload provisioning profile + dist cert.
2. `eas build -p ios --profile production`
3. `eas submit -p ios --latest` → uploads to App Store Connect.
4. In App Store Connect, add internal testers (must be on your team) — they get the build immediately after processing (~10–30 min).

**Top gotchas:**
1. Internal testers must already be on your **Apple Developer team** (App Manager, Developer, or Marketer roles can test). Random external email addresses must go via External testing + Beta App Review.
2. Builds expire after 90 days on TestFlight — set a calendar reminder, or you'll have testers reporting "expired" mid-pilot.

## 10. Observability minimum for v1 (50 testers)

**Recommendation:** **Sentry + Cloud Functions logs.** Skip Crashlytics for v1.
- **Sentry** has first-class Expo SDK support, sourcemap uploads built into EAS Build, captures both JS errors and native crashes, and works on web — so one tool covers all three platforms. Crashlytics needs `@react-native-firebase/crashlytics` (native module → can't be added later without SDK migration), has no React Native sourcemap support, and doesn't cover web at all.
- **Cloud Functions** automatically log stdout/stderr to Cloud Logging; just add structured logs (`functions.logger.info({event:'...', uid, durationMs})`) and you have a queryable trail.

**Sentry init:**
```ts
// app/_layout.tsx
import * as Sentry from '@sentry/react-native';
Sentry.init({
  dsn: process.env.EXPO_PUBLIC_SENTRY_DSN,
  environment: __DEV__ ? 'dev' : 'production',
  tracesSampleRate: 0.2,
  enableAutoPerformanceTracing: true,
});
export default Sentry.wrap(RootLayout);
```

**Top gotchas:**
1. Without sourcemap upload, every Sentry stack is `bundle.js:1:9999`. Configure `@sentry/react-native/expo` plugin in `app.config.ts` and a `SENTRY_AUTH_TOKEN` EAS secret, and let EAS Build upload maps automatically per build.
2. At 50 testers you'll be well inside Sentry's free tier (5K errors/mo). Set quota alerts at 80% so a runaway error loop doesn't burn through it overnight.

**Sources:**
- [Sentry: from Crashlytics (RN sourcemap support)](https://sentry.io/from/crashlytics/)
- [TrustRadius: Crashlytics vs Sentry 2026](https://www.trustradius.com/compare-products/firebase-crashlytics-vs-sentry)

## Cross-cutting top 3 gotchas

1. **Firebase JS SDK + Expo auth persistence is silently fragile** — `getReactNativePersistence` has wrong TS types and falls back to memory persistence if you skip the `initializeAuth` call. Test "kill app, reopen, am I still signed in?" on a real device every release.
2. **AASA + Firebase Hosting fights itself.** Without `appAssociation: "NONE"` Firebase serves its old Dynamic Links AASA at the same path — Universal Links silently break and only manifest for users in production.
3. **Firestore rules don't cascade into subcollections.** Every nested `match` block must repeat its own auth checks, or you ship a wide-open subcollection.
